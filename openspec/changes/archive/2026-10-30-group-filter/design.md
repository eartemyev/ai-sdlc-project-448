# Design

## Context

Мотивация описана в `proposal.md`. Сейчас `App.tsx` хранит `userId` и `serviceId` локально, передаёт в `NativeSelect` всех `config.users` и получает результат через `checkAccess`. `User.groupIds` уже задаёт членство; `Group` содержит `id` и `name`. `useSimulator` заменяет конфигурацию после успешного импорта, не меняя состояние выбора экрана. Соседние тесты используют Testing Library, MantineProvider и user-event; тесты редактора уже показывают подготовку конфигурации через хранилище и импорт файла.

Существующие спецификации расчёта и импорта не конфликтуют с фильтром: его состояние не входит ни в запрос расчёта, ни в формат файла. Требования поведения находятся в `specs/employee-selection/spec.md`.

## Goals / Non-Goals

**Goals:**

- Получать список вариантов и допустимый выбор из одной текущей конфигурации без скрытого выбранного сотрудника.
- Сохранить границы слоёв из `docs/architecture.md` и ограничения `docs/security-requirements.md`.

**Non-Goals:**

- Новый модуль расчёта, расширение доменной модели или формата хранения.
- Обобщённый механизм фильтров и отдельное глобальное хранилище состояния экрана.

## Decisions

### Локальный фильтр и производный список

Добавить в `App` локальный `groupId` с пустой строкой для «Все группы» и `NativeSelect` с подписью «Группа». Варианты брать из `config.groups`, сотрудников фильтровать через `groupIds.includes(groupId)` с сохранением порядка. Конфигурация приходит только из `useSimulator`; типы при необходимости импортируются через `../app`.

Альтернатива — перенести фильтр в `useSimulator` или сохранять в конфигурации. Это расширяет API и связывает состояние одного экрана с хранением без необходимости. Для текущего объёма фильтрация списка относится к представлению; отдельная абстракция не требуется.

### Согласование выбора при фильтрации и импорте

Использовать единое правило нормализации: отсутствующая группа становится пустой строкой, сотрудник сохраняется только в вычисленном списке, сервис — только в текущем справочнике. При смене группы сразу сбрасывать исключённого сотрудника. При замене конфигурации согласовать локальное состояние с ней до расчёта и отображения; сброшенные идентификаторы удалить из состояния, чтобы они не восстанавливались при следующей смене фильтра или импорте.

Для согласования при внешней замене конфигурации допустимо условное обновление локального состояния при обнаружении изменившейся ссылки `config`, с обязательной проверкой, исключающей цикл рендера. Расчёт и поля используют уже нормализованные значения в том же рендере. Альтернатива — один эффект после отображения; без защиты он допускает кадр со старым результатом и не соответствует требованию согласованности. Изменения разрешений сохраняют допустимый выбор, не сбрасывая его по одному лишь изменению ссылки `config`.

### Полный расчёт и явное пустое состояние

`checkAccess` получает только допустимые `userId` и `serviceId` и полную конфигурацию через существующий хук. Фильтр не передаётся в расчёт или `PermissionsPanel`. При пустой группе оставлять вариант «Не выбран» и выводить «В группе нет сотрудников»; автоматического выбора первого участника нет.

Альтернатива — сузить конфигурацию до выбранной группы до расчёта. Она потеряет независимые источники доступа и нарушит существующий контракт.

### Проверка поведения через экран

Реализация ведётся скиллом `tdd`: каждый сценарий добавляется как падающий тест, затем минимальная реализация и рефакторинг. Расширить `App.test.tsx` сценариями новой спецификации, используя существующий способ подготовки конфигурации. Проверять варианты внутри конкретного поля через `within`, результат, источники, экспорт и сохранённый текст. Нужны данные с несколькими группами у сотрудника, пустой группой, сотрудником без групп и командой из восьми человек.

## Risks / Trade-offs

- Скрытый старый выбор после импорта → нормализация до вызова `checkAccess` и тесты замены конфигурации, изменения членства и отклонённого импорта.
- Случайное ограничение источников выбранной группой → тест прямого разрешения и разрешения другой группы одновременно.
- Совпадающие имена групп → значения вариантов используют идентификаторы; отображение имён сохраняет существующий подход справочников.
- Лишние сбросы при выдаче или отзыве → сохранять любой выбор, допустимый в новой конфигурации.

## Migration Plan

Миграция данных не нужна: используется существующее членство, фильтр не сериализуется. После обычной сборки и публикации статических файлов экран начинает с «Все группы». Откат изменения интерфейса не требует изменения сохранённых данных.
